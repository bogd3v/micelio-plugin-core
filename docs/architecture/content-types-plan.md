# The content types plan

**Kind:** plan (proposal). For the maintainer, who approves it, and for the planner and workers who cut implementation issues from it. It decides nothing by itself and changes no schema, route, migration or component: what it proposes becomes a decision when the maintainer approves the issue list at the end, and the ADR-0017 amendments in "Amendments" become an ADR change when the first issue that needs one ships. It is the plan that the amendment of 2026-10-26 (D8) of [ADR-0017](https://github.com/bogd3v/micelio/blob/main/docs/adr/0017-distribution-plugins-multisite-editorial.md) leaves to `micelio-plugin-core`: "article, page, author and the rest follow a plan of `micelio-plugin-core`, which this record does not make". It is the plan for the milestone "Tipos de contenido al core" that row 11 of the issue list of [`docs/architecture/block-catalogue-plan.md`](https://github.com/bogd3v/micelio/blob/main/docs/architecture/block-catalogue-plan.md) names (Part of bogd3v/micelio#872; planning issue bogd3v/micelio-plugin-core#195).

## Why a plan

ADR-0017 section 2 moves the content types of `micelio-cms` into `@micelio/strapi-plugin-core` as `plugin::micelio.<type>`, one type at a time and each in the release where the core ships it (D8). Two types moved (`category` and `tag`, bogd3v/micelio-plugin-core#88) and `site-setting` became `site`. Seven types of `micelio-cms` are still its own, and three things wait for them:

- **The reusable block.** A core type cannot target a host type (D5), so the core's `reusable-block` (row 11 of the catalogue plan, ADR-0022 section 1), which must list and refuse on the pages that reference it, needs `page` in the core.
- **The block catalogue.** Its schema wave 0 lands before this move because a UID change after it costs more, and the absorption of the About blocks (row 45 of the catalogue plan) goes with the move of the page type.
- **The registry.** After a registry accepts third-party themes (bogd3v/micelio#404) a UID change costs a MAJOR (D8). Every move below is planned before that.

**The rules the plan keeps** (ADR-0017 and standard, sections 6 and 7): CMS first, every contract keyed by site, boot migrations idempotent and self-contained, the upgrade from the last release with no manual step. Before 1.0.0 a breaking change raises `y`. A move changes the action name of every permission on the type (`api::page.page.find` becomes `plugin::micelio.page.find`), so a Custom API token an operator made by hand must change: each move is breaking for operators and raises `y`, as the move of `category` and `tag` did.

**"Moves together"** means the types are in the same release because a relation joins them: a core type cannot declare an attribute that targets a host type (D5), so the two ends of such a relation are in the core together or not at all, and the host adds the inverse side to a core type meanwhile.

### What the fediverse plugin and the comments plugin store

Two plugins that the CMS installs keep the UID of `article` in their data or code, and neither is the core's to change:

- `strapi-plugin-comments` stores `related` as `api::article.article:<documentId>` in its table, is configured with the UID, and the frontend sends the same string (above).
- `@micelio/strapi-plugin-fediverse` has the constants `ARTICLE_UID = 'api::article.article'` and `GLOBAL_UID = 'api::global.global'` (`fediverse: server/src/constants/uids.ts`), listens to the Document Service events of the first (`withoutEditorial: true`, as `article` has no `editorial` component) and the changes of the second, and builds the comment relation prefix from them (`server/src/services/stats.ts`, `replies.ts`, `reply-notes.ts`). Its `docs/operate/configure.md` lists both types as what the host must provide.

## Per type, the move

Each type has one proposal. "Release" is the proposal of "The order" below.

### page, and the components

- **UID.** `plugin::micelio.page`, table `pages`, kept; the same `slug`, `title`, `seo` and `sections`.
- **Components.** `page` cannot move without the 14 `section.*` blocks and their parts, `shared.seo` and what `seo` carries, since a core type that depends on host components does not install on its own. They move to the core under their own UIDs (`section.hero`, `shared.seo`, and so on) with their `collectionName`, so the tables of the components (`components_section_heroes`) and the `component_type` strings stored in the `pages_cmps` link table are not touched. The alternative, a category of the core (`micelio-block.hero`, as the site's components are `micelio-site.*`), is a data migration of every stored block; see "Open decisions", 2. `core: contract/blocks.ts` names the `post-list` relations as `api::category.category` and `api::tag.tag`, while the CMS component targets `plugin::micelio.category` and `plugin::micelio.tag`: the issue that moves the components settles which one the contract says.
- **Route.** `/api/pages` and `/api/pages/:id` kept, with the five actions' site-scope middleware as today (`prefix: ''`, as `routes/taxonomy.ts` does for `/api/categories`); no alias is needed.
- **Rename step.** The legacy-UID step (`core: server/src/migrations/rename-legacy-uids.ts`, on `strapi::content-types.beforeSync`) gains `api::page.page` to `plugin::micelio.page` for the actions of roles and API tokens, the admin permission subjects and the Content Manager layouts, in the same map, self-contained. The admin permission rows that `admin-page-site` writes name the type as well.
- **D5 extension it removes.** `homePage` on `site`: it moves into the core's `site` schema in the same release (`oneToOne`, localised, target `plugin::micelio.page`), and `cms: src/extensions/micelio/strapi-server.ts` loses it. The core's export of `site` then carries it: the `site` row of `core: docs/export-format.md` does not list it today, and `cms: docs/architecture/micelio-plugin.md` says an export of the core does not carry it until the page type moves.
- **Site scoping.** Already (`withSiteScope`); it keeps the `site` relation and the default-site backfill in the core (as `site-backfill.ts` does for the taxonomy) so a host that has no `page-site` still serves its pages.
- **Editorial.** Not in the move (D7, "Open decisions", 4). With `withEditorial` the Content Manager's publish is refused and publishing needs the budget measurement from a reachable frontend (`core: docs/operate/budgets.md`); neither is a behaviour of the move. `withPageSettings` is another matter: `cms#414` applies it to the host's page, and it is cheaper to land first ("Open decisions", 3).
- **Export section.** The row of `api::page.page` in `core: docs/export-format.md` becomes `plugin::micelio.page`; the export name `page` never changes (ADR-0017, section 2).
- **Upgrade test.** `cms: scripts/upgrade-check/` (`npm run test:upgrade`, default `UPGRADE_FROM_IMAGE` `ghcr.io/bogd3v/micelio-cms:0.6.0`, to be `0.7.0`) counts rows and permissions before and after, and its `SEEDED` list holds `pages`. Add the grant of a hand-made Custom token on `api::page.page.find`, and the Content Manager layout. The core's own proof is the model of `core: test/strapi/taxonomy-takeover.test.ts` with a fixture of the CMS `0.7.0` page schema (as `test/fixtures/micelio-cms-v0.5.0-taxonomy-schemas.json` is for the taxonomy).
- **Content history.** The Content Manager keeps history only for `api::` types (`@strapi/content-manager` `5.59.0`, `history/services/lifecycles.js` returns for a UID that does not start with `api::`), so the versions of a page stop being recorded and the old ones are not listed. The amendment of 2026-10-21 recorded the same loss for the taxonomy. Proposed: accept, and say it in the upgrade notes.
- **Release.** L1 (below).

### author and article, together

- **Why together.** `article.author` and `author.articles` are one relation, and `category.articles` and `tag.articles` are the inverses of `article.category` and `article.tags` (D5). The core cannot declare an attribute that targets a host type, so `article` and `author` move in one release, and the two inverses move into the core's `category` and `tag` with them. The D5 extension (`cms: src/extensions/micelio/strapi-server.ts`) is removed whole: its file goes with the release.
- **UID.** `plugin::micelio.author` and `plugin::micelio.article`, tables `authors` and `articles` kept. The `article.category` and `article.tags` targets already are `plugin::micelio.category` and `plugin::micelio.tag`.
- **Routes.** `/api/articles` and `/api/authors` with `prefix: ''`. `GET /api/articles/search` moves to the core with the article service, since it has no host concept. `GET /api/articles/drafts` stays in the distribution: its policy `global::is-editor` (`cms: src/policies/is-editor.ts`) belongs to the host's Editor role, a role of `users-permissions` that `editor-role.ts` creates and the core does not know. The host route points at the core controller (`plugin::micelio.article.drafts`) and registers first, as `core: docs/api.md` ("A host with its own `/api/categories`") says host routes do. `GET /api/articles/popular` stays with `article-stat`, for the same reason and the same rule: the host's route must register ahead of the core's `/api/articles/:id`. The rule is stated in `core: docs/api.md` and no test of the core covers it; the amendment of 2026-10-21 lists a collision between a host route and a plugin route as not verified, and it is the first thing the spike checks.
- **Rename step.** The same map and tables as `page`, for both UIDs, plus what the taxonomy did not have: `article.cover` and `author.avatar` are media, and the upload plugin's `related` is a `morphToMany` (`@strapi/upload` `5.59.0`, `content-types/file.js`), so the join table of the files holds the owner's UID in a type column. The step must rename it; no test of the taxonomy covers it. `comments.related` (the host's plugin) is renamed by the distribution's own migration, and the CMS answers `GET /api/comments?relation=api::article.article:<id>` from the previous MINOR frontend by mapping the old string to the new one in a middleware, as the CMS of a line serves the previous MINOR frontend (`cms: docs/operate/upgrade.md`, "The rules"). `strapi_history_versions` and `strapi_release_actions` are not renamed: history stops for the type (above), and a release that names an article by UID is an open question for the spike.
- **D5 extensions it removes.** `articles` on `category` and `tag`. They move into the core's schemas with the types.
- **Site scoping.** New: neither type has a `site` relation today. They gain `withSiteScope` and a backfill that gives the rows with no site the default site, as `cms: src/migrations/page-site.ts` and the core's taxonomy backfill do. A request without a site still gets the default site, so the frontend is unchanged. For `author`, see "Open decisions", 5.
- **What moves with the article.** `check-citations.ts`, `citations.ts` and `plain-text.ts`, the `plainText` derivation, the image-credit check for the article, the author-locale middleware and its `plugin::i18n.locale` lifecycle, and `ensureAuthorLocales`. The rebuild hook (`cms: src/utils/rebuild-hook.ts`) lists the UIDs it listens to and changes them (or moves to the core's `afterPublish` hooks, when the type is editorial). `restrictDraftsToEditors` stays in the distribution.
- **Plugins that name the UID.** The fediverse plugin must read the article UID from one place that accepts both until the CMS moves (a change of `fediverse: server/src/constants/uids.ts`); it ships before the CMS release, as the CMS-first rule asks. The comments `entryRelation` and `enabledCollections` in `cms: config/plugins.ts` change with the CMS.
- **Frontend.** The comment relation pattern and the `uid` of the preview routes accept both UIDs for one release line (`micelio: app/helpers/comments.ts`, `app/constants/preview.ts`, `server/openapi/routes/`), then only the new one.
- **Editorial.** Not in the move. The fediverse plugin federates an article by the `eventHub` events because it has no `editorial` component (`fediverse: docs/operate/configure.md`); the move keeps that path working, and `withEditorial` later switches it to the core's hooks without a gap because the plugin handles both.
- **Export section.** `api::article.article` and `api::author.author` rows of `core: docs/export-format.md`: neither is in an archive today, since the exporter writes only the types made with `withSiteScope` and the `site` (`core: server/src/site-export/model.ts`). After the move they are, with the names `article` and `author` that the document already reserves; `plainText` is rebuilt on import (the derivation lives in the core by then), `author.email` is `personal`, and `category.articles` and `tag.articles` become the inverse sides of a relation that the plugin owns whole.
- **Upgrade test.** As for `page`, plus: `files_related_mph` rows by owner type before and after, the comments' `related`, a fediverse follower and a federated article kept (`cms: scripts/upgrade-check/fediverse.mjs` already seeds them), and the Editor role's `drafts` grant.
- **Release.** L2.

### about

- **Decision proposed.** It does not move as a type. `about` becomes a `page` with the slug `about` on the default site, in every locale it has; the type is retired under the D6 rule; the route is kept for one release (see "The About page" for why and how).
- **UID taken.** None: its data go to `plugin::micelio.page`; `api::about.about` stays in the CMS for one release, hidden, never written, and is removed in the next MINOR.
- **Site scoping, editorial.** As the page's, since it is a page.
- **Export section.** None of its own: an archive writes the page. The row of `api::about.about` in `core: docs/export-format.md` is reworded to say that only an instance before the move holds it, as the row of `api::site-setting.site-setting` says.
- **Release.** L3, after the catalogue blocks the About page is built from.

### global

- **Decision proposed.** It does not move and is not a type of the core. Its four attributes have a home in `site`: `siteName` and `siteDescription` are what `site.name` and `site.description` hold; `favicon` is `site.favicon`; `defaultSeo` has no reader in the frontend (`micelio` has no `defaultSeo`). Its only reader is the fediverse plugin (above).
- **The retirement.** (1) The fediverse plugin reads the default site's `favicon`, `name` and `description` and no longer `api::global.global`; (2) the distribution copies `global.favicon` into the default site only when that is empty, as `site-settings-to-site` copies "never over a value the site already holds", and reports the rest, in the way `fediverse-header` did; (3) the type is hidden for one release and removed in the next MINOR (D6). Nothing in the core changes, so the core has no issue.
- **Release.** L3; (1) ships before (2).

### subscriber

- **Decision proposed.** It stays a host type: `api::subscriber.subscriber` is the distribution's, not the core's. Nothing of the block contract, the editorial workflow or the host check refers to it; the `newsletter` section posts to the frontend, not to the core.
- **Why not the core.** The core has no newsletter, and ADR-0017 section 1 expects each optional capability as its own package ("newsletter, search, documentation publishing, preservation"). A subscriber is personal data that the exporter treats as `personal`; a plugin that owns it should own the confirmation, the purge and the mail, which are the distribution's today.
- **Cost of leaving it.** If the newsletter package is built it takes `api::subscriber.subscriber` over with a rename step like #88's, and that move costs a MAJOR of the CMS if it happens after a registry accepts third-party themes (D8's reason); "Open decisions", 6, asks whether the plan commits to a package before then.
- **Site scope.** None today and none proposed here: a subscriber has no `site` column, and a multi-site newsletter is a decision of that package.
- **Release.** None.

### article-stat

- **Decision proposed.** It stays a host type, hidden, and belongs with an analytics package if one is built. It keys the article by `documentId` and locale as strings, so the move of `article` does not change its rows; its service imports `ARTICLE_UID` and reads the articles through it, so it changes to the new UID in the release of `article` (a line in the CMS's article issue, not an issue of its own).
- **Route.** `GET /api/articles/popular` stays, registered ahead of the core's `/api/articles/:id` (above).
- **Release.** None of its own.

### site-setting

- **Decision.** Already taken (D6): removed from the distribution in `0.8`, the next MINOR after `0.7`. This plan adds the order: the removal ships in L1 and the alias route `GET /api/site-setting` goes with it, so the frontend must read the default site from the core's `GET /api/micelio/sites` (`core: docs/api.md`, "Routes") before L1, in the files that call the alias today (`micelio: server/utils/site.ts`, `modules/static-routes.ts`, `modules/theme/static-theme.ts`, `scripts/lib/static-generate.mjs`). That route answers in another shape than the alias, which strips the attributes only a site has, and the tokens would need the site's read action; neither was compared (C16). D6 states the schema-sync risk (dropping `site_settings` before a copy on a skipped release) as not verified; the spike covers it.
- **D5.** `homePage` leaves its schema with the page's move.

## The order

Four things hold the order: a relation joins two types (they move together), the components move before the types that use them, a CMS release needs the core release that carries the type, and the frontend and the plugins that name a UID accept both before the CMS runs the new UID (C6 before C5, C9 and C10 before C8): the frontend of the previous line keeps its preview, its comments and its drafts while the CMS upgrades.

```text
C1  spike                         <- none
C2  ADR-0017 amendment            <- C1, approval of this plan
C3  components (core)             <- C1, C2, catalogue rows 1 to 5
C4  page + site.homePage (core)   <- C3, cms#414
C6  frontend accepts both pages   <- C4
C5  CMS runs page                 <- C4, C6
C14 row 11 pointer                <- approval of this plan   (row 11 of the catalogue plan starts when C4 is merged)
C7  author + article (core)       <- C3, C4
C9  fediverse accepts both        <- C7
C10 frontend accepts both article <- C7
C8  CMS runs author + article     <- C7, C9, C10
C11 about becomes a page (CMS)    <- C5, catalogue rows 4, 17, 26, 39, 40, 42
C12 frontend renders /about       <- C11
C13 global retired (CMS)          <- C9
C16 frontend reads /micelio/sites <- none
C15 site-setting removed (CMS)    <- C1, C5, C16
```

**Moves together.**

- **L1: the components, `page`, `site.homePage`.** `page` and `site.homePage` are one relation; the components are the page's zone. `post-list` targets `plugin::micelio.category` and `tag`, already in the core, so nothing of the taxonomy joins.
- **L2: `author`, `article` and the inverse `articles` of `category` and `tag`.** Three relations, all in one release (above). `article` needs the `shared.*` components, so it follows L1.
- **L3: `about` becomes a page, and `global` is retired.** They are independent of each other and of L2 (about needs only the page and the catalogue blocks; global needs only the fediverse plugin); they ride together because both are D6 retirements and share a release note.

**Where row 11 of the catalogue plan can start.** The `reusable-block` type lists and refuses on pages, so it needs `plugin::micelio.page` and the block components in the core, which is C4. It does not need L2 or L3. Row 11 starts when C4 is merged, not when the whole cut-over is. The proposal changes the dependency of row 11 from the milestone to C4 (C14), and rows 12 and 13 follow it unchanged.

**What can start now.** C1 (the spike), C14 (the pointer) and C16 (the frontend reads the site by the core's route) need nothing; the rest wait for the spike or for catalogue wave 0.

**Release lines.** `micelio-cms` is at `0.7.0`, so L1 is `0.8` at the earliest, and each of L1, L2 and L3 raises `y` (the permission actions change names): `0.8`, `0.9`, `0.10`, with the core minors that declare them. The numbers are a proposal; `scripts/release/version.mjs` and the release plan decide them. If the maintainer prefers fewer breaking lines, "Open decisions", 13 gives the cost of one line.

## The About page

### Does `about` become a page?

Proposed: yes. `api::about.about` is a single type with a zone of its own (`blocks`: seven `about.*` blocks and the four article-zone blocks), `seo` and a `title`; a page has the same three things and, with the catalogue's blocks, the same expressiveness. The catalogue plan already assumes it: "After the cut-over the About page is a page, so it has no zone of its own". Keeping a second page-like type in the core would need its own block zone, its own export row, its own builder entry and a second place to apply `withSiteScope` and `withPageSettings`.

### What retiring `api::about.about` means

Under the D6 rule the type keeps its schema for one release after the copy, hidden from the Content Manager and the Content-Type Builder, never written, and is removed in the next MINOR. Three things follow:

- **The route.** D6 says "no routes of its own", and `site-setting` kept `GET /api/site-setting` as an alias because the previous MINOR frontend still reads it (D3). For `about` the alias cannot answer from the page, because the previous frontend's answer has `about.*` blocks that a page no longer holds. The proposal is a frozen alias: `GET /api/about` keeps answering from the retained rows for one release line, unchanged, so the previous MINOR frontend still renders its page while the new frontend reads the page of slug `about`. It departs from D6's wording, hence amendment A1.
- **The frontend.** `micelio: app/pages/about.vue` and `server/api/about.get.ts` (and `fetchAbout` in `app/composables/useStrapi.ts`, `aboutSchema` in `app/schemas/blocks.ts`) are retired: the path `/about` is rendered by `app/pages/[slug].vue` for the page of that slug. `GET /api/about` of the frontend is a documented route (`micelio: server/openapi/routes/content.ts`, `docs/openapi.json`); it is removed with a note in the frontend's release (its answer cannot be rebuilt from a page). The `/about` entries of the sitemap and the header (`server/routes/sitemap.xml.ts`, `app/helpers/header.ts`, `app/composables/useNavLinks.ts`) name the path, which does not change, so they need no edit.
- **The data.** The migration copies `title` and `seo` (the same `shared.seo` component) and converts `blocks` into `sections`, in every locale the About page has, as a published page of the default site with the slug `about` (the single type has no draft, so a draft is not a state it can carry). It is idempotent (a page with that slug in that locale is never touched again) and writes through the database layer so no publish event fires and the rebuild hook stays quiet, as `page-site` does.

### Whose migration is it

Proposed: the distribution's. The `about.*` components and `api::about.about` belong to `micelio-cms`, which seeds an About page in its demo (`cms: src/migrations/demo-seed.ts`); any instance of the distribution has `about.*` rows, not only BogDev's. The core never sees an `about.*` component (standard, principle 2: no site's content in the core, and ADR-0018, section 6, keeps them out of the catalogue). So the migration is `cms: src/migrations/about-to-page.ts` in the release that carries the page, generic over the shape of the blocks and never over a site's values; it needs the core's `page` (C5) and the blocks above (catalogue rows 4, 17, 26, 39, 40 and 42), and it replaces row 45 of the catalogue plan, which is not opened. "Open decisions", 8, gives the alternative.

If `withEditorial` is on the page by then, the migration's publish must not go through the Document Service (the guard refuses it), so it writes below it; it is another reason to keep editorial out of the move.
